Instead of writing runtime logic to validate data, you encode constraints directly into the type system.\n\n```typescript\n// Runtime validation (traditional)\nfunction validateUser(data: unknown): data is User {\n  return typeof data === 'object' && \n         data !== null &&\n         'name' in data && \n         typeof data.name === 'string'\n}\n\n// Type-level validation (with typist)\ntest_('user structure validation', () => {\n  type User = { name: string; age: number }\n  const user = t_<User>()\n  \n  has_<'name', string>(user)    // ✓ Required property\n  has_<'age', number>(user)     // ✓ Required property\n  never_<User & { invalid: any }>() // ✓ No extra properties\n})\n```\n\n### When to Use Type-Level Programming\n\n**Ideal Use Cases**:\n- API contract validation\n- Configuration schema verification  \n- Library type safety guarantees\n- Complex generic type constraints\n- Code generation and metaprogramming\n- Static analysis and linting\n\n**Avoid When**:\n- Simple type assignments work fine\n- Runtime performance is critical\n- Type errors would be too complex for team\n- Build time is already slow\n\n---\n\n## Phantom Types\n\nPhantom types are the foundation of type-level programming with typist. They represent type information without runtime values.\n\n### Basic Phantom Types\n\n```typescript\nimport { t_, phantom_ } from '@typefirst/typist'\n\n// Create phantom values\nconst str = t_<string>()\nconst num = t_<number>()\nconst user = t_<{ name: string; age: number }>()\n\n// Use phantom values for type operations\nis_<string>(str)\nis_<number>(user.age)\nis_<string>(user.name)\n```\n\n### Advanced Phantom Patterns\n\n#### Generic Type Construction\n\n```typescript\n// Generic phantom factory\nfunction createRecord<K extends string, V>(): Record<K, V> {\n  return t_<Record<K, V>>()\n}\n\nconst userRecord = createRecord<'name' | 'email', string>()\nis_<string>(userRecord.name)\nis_<string>(userRecord.email)\n```\n\n#### Conditional Phantom Types\n\n```typescript\ntype ApiResponse<T> = T extends string \n  ? { message: T }\n  : { data: T }\n\nfunction response<T>(): ApiResponse<T> {\n  return t_<ApiResponse<T>>()\n}\n\nconst stringResponse = response<string>()\nconst dataResponse = response<{ users: User[] }>()\n\nis_<{ message: string }>(stringResponse)\nis_<{ data: { users: User[] } }>(dataResponse)\n```\n\n#### Phantom Type Composition\n\n```typescript\n// Combine phantom types\nconst combined = intersect_<\n  { id: string },\n  { metadata: { created: Date } }\n>()\n\nis_<string>(combined.id)\nis_<Date>(combined.metadata.created)\n\n// Union phantoms for variant types\nconst either = union_<\n  { type: 'success'; data: string },\n  { type: 'error'; message: string }\n>()\n```\n\n### Phantom Type Utilities\n\n#### Value Assignment with Constraints\n\n```typescript\n// Constrain values to specific types\nconst strictString = assign_<string>('hello')     // ✓ string literal → string\nconst widened = widen_<string>('constant')        // ✓ Explicit widening\n\n// Build objects with type constraints  \nconst user = assign_<User>({\n  name: 'Alice',\n  age: 30\n})\n```\n\n#### Type Resolution and Normalization\n\n```typescript\n// Resolve complex types to readable forms\ntype Complex = Promise<{ items: Array<{ id: string }> }>\nconst resolved = resolve_<Complex>()\n// Better IDE experience with simplified types\n\n// Flush readonly/mutable variations\ntype ReadonlyData = { readonly items: readonly string[] }\nconst flushed = flush_<ReadonlyData>()\n// Normalized for comparison operations\n```\n\n---\n\n## Static Testing\n\nStatic testing validates type relationships at compile time, catching errors before runtime.\n\n### Test Organization\n\n```typescript\n// Group related assertions\ntest_('user type safety', () => {\n  type User = { name: string; age: number; active: boolean }\n  const user = t_<User>()\n  \n  // Property type validation\n  is_<string>(user.name)\n  is_<number>(user.age)\n  is_<boolean>(user.active)\n  \n  // Structural validation\n  yes_<$Equal<User, typeof user>>()\n  \n  // Property existence\n  has_<'name', string>(user)\n  has_<'age', number>(user)\n  has_<'active', boolean>(user)\n})\n```\n\n### Testing Type Relationships\n\n```typescript\ntest_('inheritance and extension', () => {\n  type Animal = { species: string }\n  type Dog = Animal & { breed: string }\n  type Cat = Animal & { indoor: boolean }\n  \n  // Subtype relationships\n  extends_<Dog, Animal>()        // ✓ Dog extends Animal\n  extends_<Cat, Animal>()        // ✓ Cat extends Animal\n  \n  // Mutual exclusivity\n  never_<Dog & Cat>()            // ✓ No overlap\n  \n  // Union behavior\n  const pet = union_<Dog, Cat>()\n  is_<string>(pet.species)       // ✓ Common property\n})\n```\n\n### Testing Generic Constraints\n\n```typescript\ntest_('generic type constraints', () => {\n  // Test generic utility types\n  type KeysOfType<T, U> = {\n    [K in keyof T]: T[K] extends U ? K : never\n  }[keyof T]\n  \n  type User = { name: string; age: number; active: boolean }\n  type StringKeys = KeysOfType<User, string>    // 'name'\n  type NumberKeys = KeysOfType<User, number>    // 'age'\n  type BooleanKeys = KeysOfType<User, boolean>  // 'active'\n  \n  yes_<$Equal<StringKeys, 'name'>>()\n  yes_<$Equal<NumberKeys, 'age'>>()\n  yes_<$Equal<BooleanKeys, 'active'>>()\n})\n```\n\n### Testing Error Conditions\n\n```typescript\ntest_('error condition validation', () => {\n  // Test that invalid operations fail\n  never_<string & number>()               // ✓ Impossible intersection\n  never_<'hello' & 'world'>()             // ✓ Incompatible literals\n  \n  // Test negative verdicts\n  no_<$Equal<string, number>>()\n  no_<$Extends<string, number>>()\n  \n  // Test impossible property access\n  type Empty = {}\n  never_<Empty['nonexistent']>()          // ✓ Property doesn't exist\n})\n```\n\n---\n\n## Type Comparisons\n\nThe verdict system provides rich information about type relationships.\n\n### Understanding Verdicts\n\nVerdicts encode the result of type-level computations:\n\n```typescript\n// Successful comparisons return $Yes\ntype Success = $Equal<string, string>              // → $Yes\ntype SubtypeOk = $Extends<'hello', string>         // → $Yes\n\n// Failed comparisons return $No with details\ntype Failure = $Equal<string, number>              // → $No<'not-equal', [string, number]>\ntype NoExtends = $Extends<string, number>          // → $No<'right-does-not-extend-left', [string, number]>\n```\n\n### Custom Comparators\n\nBuild your own verdict-returning type utilities:\n\n```typescript\n// Custom array length comparison\ntype $ArrayLengthEqual<T1 extends readonly any[], T2 extends readonly any[]> =\n  T1['length'] extends T2['length']\n    ? T2['length'] extends T1['length']\n      ? $Yes\n      : $No<'length-mismatch', [T1['length'], T2['length']]>\n    : $No<'length-mismatch', [T1['length'], T2['length']]>\n\ntest_('custom array length comparison', () => {\n  type Same = $ArrayLengthEqual<[1, 2, 3], ['a', 'b', 'c']>    // → $Yes\n  type Different = $ArrayLengthEqual<[1, 2], [1, 2, 3]>       // → $No<...>\n  \n  yes_<Same>()\n  no_<Different>()\n})\n```\n\n### Complex Comparison Patterns\n\n```typescript\n// Deep object structure comparison\ntype $DeepEqual<T1, T2> = \n  T1 extends object\n    ? T2 extends object\n      ? {\n          [K in keyof T1]: K extends keyof T2 \n            ? $DeepEqual<T1[K], T2[K]>\n            : $No<'missing-property', [K]>\n        }[keyof T1] extends $Yes\n        ? {\n            [K in keyof T2]: K extends keyof T1\n              ? $Yes\n              : $No<'extra-property', [K]> \n          }[keyof T2] extends $Yes\n          ? $Yes\n          : $No<'structure-mismatch', [T1, T2]>\n        : $No<'property-mismatch', [T1, T2]>\n      : $No<'type-mismatch', [T1, T2]>\n    : $Equal<T1, T2>\n\ntest_('deep structure comparison', () => {\n  type User1 = { profile: { name: string; age: number } }\n  type User2 = { profile: { name: string; age: number } }\n  type User3 = { profile: { name: string; email: string } }\n  \n  yes_<$DeepEqual<User1, User2>>()\n  no_<$DeepEqual<User1, User3>>()\n})\n```\n\n---\n\n## Building Complex Type Utilities\n\nCombine typist utilities to build sophisticated type-level tools.\n\n### Path-Based Access Utilities\n\nImplement type-safe deep property access:\n\n```typescript\n// Type-level path navigation\ntype GetAtPath<Obj, Path extends readonly PropertyKey[]> =\n  Path extends readonly [infer Head, ...infer Tail]\n    ? Head extends keyof Obj\n      ? Tail extends readonly PropertyKey[]\n        ? GetAtPath<Obj[Head], Tail>\n        : Obj[Head]\n      : never\n    : Obj\n\n// Runtime implementation with type safety\nfunction getAtPath<T, P extends readonly PropertyKey[]>(\n  obj: T, \n  path: P\n): GetAtPath<T, P> {\n  return path.reduce((current: any, key) => current?.[key], obj)\n}\n\ntest_('path-based access validation', () => {\n  type Data = {\n    user: {\n      profile: { name: string; settings: { theme: 'dark' | 'light' } }\n      posts: Array<{ title: string; published: boolean }>\n    }\n  }\n  \n  const data = t_<Data>()\n  \n  // Type-safe path access\n  is_<string>(getAtPath(data, ['user', 'profile', 'name']))\n  is_<'dark' | 'light'>(getAtPath(data, ['user', 'profile', 'settings', 'theme']))\n  \n  // Invalid paths are caught at compile time\n  // never_<GetAtPath<Data, ['user', 'invalid']>>()\n})\n```\n\n### Schema Validation Utilities\n\nCreate compile-time schema validators:\n\n```typescript\n// Schema definition types\ntype StringSchema = { type: 'string'; minLength?: number }\ntype NumberSchema = { type: 'number'; min?: number; max?: number }\ntype ObjectSchema<T = any> = { type: 'object'; properties: T }\ntype Schema = StringSchema | NumberSchema | ObjectSchema\n\n// Type-level schema validation\ntype ValidateSchema<Data, S extends Schema> = \n  S extends { type: 'string' }\n    ? Data extends string ? $Yes : $No<'not-string', [Data]>\n    : S extends { type: 'number' }\n      ? Data extends number ? $Yes : $No<'not-number', [Data]>\n      : S extends { type: 'object'; properties: infer Props }\n        ? Data extends object\n          ? Props extends Record<string, Schema>\n            ? {\n                [K in keyof Props]: K extends keyof Data\n                  ? ValidateSchema<Data[K], Props[K]>\n                  : $No<'missing-property', [K]>\n              }[keyof Props] extends $Yes\n              ? $Yes\n              : $No<'property-validation-failed', [Data, Props]>\n            : $No<'invalid-schema', [Props]>\n          : $No<'not-object', [Data]>\n        : $No<'unknown-schema', [S]>\n\ntest_('schema validation', () => {\n  type UserSchema = {\n    type: 'object'\n    properties: {\n      name: { type: 'string' }\n      age: { type: 'number' }\n    }\n  }\n  \n  type ValidUser = { name: string; age: number }\n  type InvalidUser = { name: string; age: string }  // age should be number\n  \n  yes_<ValidateSchema<ValidUser, UserSchema>>()\n  no_<ValidateSchema<InvalidUser, UserSchema>>()\n})\n```\n\n### Type-Level State Machines\n\nModel state transitions at the type level:\n\n```typescript\n// State machine definition\ntype OrderStates = 'pending' | 'processing' | 'shipped' | 'delivered' | 'cancelled'\n\ntype OrderTransitions = {\n  pending: 'processing' | 'cancelled'\n  processing: 'shipped' | 'cancelled' \n  shipped: 'delivered'\n  delivered: never\n  cancelled: never\n}\n\n// Type-level transition validation\ntype ValidTransition<From extends OrderStates, To extends OrderStates> =\n  To extends OrderTransitions[From] ? $Yes : $No<'invalid-transition', [From, To]>\n\ntest_('state machine transitions', () => {\n  // Valid transitions\n  yes_<ValidTransition<'pending', 'processing'>>()\n  yes_<ValidTransition<'processing', 'shipped'>>()\n  yes_<ValidTransition<'shipped', 'delivered'>>()\n  \n  // Invalid transitions\n  no_<ValidTransition<'delivered', 'processing'>>()\n  no_<ValidTransition<'shipped', 'pending'>>()\n  no_<ValidTransition<'cancelled', 'processing'>>()\n})\n```\n\n---\n\n## Error Handling and Debugging\n\n### Understanding Error Messages\n\nType-level errors can be complex. Here's how to interpret and debug them:\n\n```typescript\n// Example: Complex error scenario\ntest_('debugging complex errors', () => {\n  type ComplexType = {\n    data: {\n      items: Array<{\n        id: string\n        metadata: {\n          tags: readonly string[]\n          priority: 1 | 2 | 3\n        }\n      }>\n    }\n  }\n  \n  const complex = t_<ComplexType>()\n  \n  // This will show detailed error information\n  // is_<number>(complex.data.items[0].metadata.priority)  // Should pass\n  // is_<string>(complex.data.items[0].metadata.priority)  // Would fail with detailed error\n})\n```\n\n### Debugging Strategies\n\n#### 1. Use Explicit Type Annotations\n\n```typescript\n// Instead of implicit inference\nconst implicit = t_<{ data: { nested: { value: string } } }>()\n\n// Use explicit types for clarity\ntype NestedData = {\n  data: {\n    nested: {\n      value: string\n    }\n  }\n}\nconst explicit = t_<NestedData>()\n```\n\n#### 2. Break Down Complex Assertions\n\n```typescript\n// Instead of one complex assertion\n// is_<ComplexType>(veryComplexExpression())\n\n// Break into steps\nconst step1 = t_<StepOneType>()\nconst step2 = t_<StepTwoType>()\nis_<StepOneType>(step1)\nis_<StepTwoType>(step2)\nis_<ComplexType>(combine(step1, step2))\n```\n\n#### 3. Use Verdict Messages for Debugging\n\n```typescript\n// Custom error messages in comparators\ntype $IsValidEmail<T> = T extends `${string}@${string}.${string}`\n  ? $Yes\n  : $No<'invalid-email-format', [T]>\n\ntest_('email validation debugging', () => {\n  type Valid = $IsValidEmail<'user@domain.com'>     // → $Yes\n  type Invalid = $IsValidEmail<'notanemail'>        // → $No<'invalid-email-format', ['notanemail']>\n  \n  yes_<Valid>()\n  no_<Invalid>()  // Error message will show: $No<'invalid-email-format', ['notanemail']>\n})\n```\n\n### Common Error Patterns\n\n#### Type Instantiation Too Deep\n\n```typescript\n// Problem: Infinite recursion in type system\ntype BadRecursive<T> = {\n  value: T\n  nested: BadRecursive<T>  // This will cause \"Type instantiation is excessively deep\"\n}\n\n// Solution: Add termination condition\ntype GoodRecursive<T, Depth extends number = 0> = \n  Depth extends 5  // Limit recursion depth\n    ? never\n    : {\n        value: T\n        nested?: GoodRecursive<T, [0, ...Array<Depth>]['length']>\n      }\n```\n\n#### Union Distribution Issues\n\n```typescript\n// Problem: Unexpected union distribution\ntype DistributionProblem<T> = T extends string ? `prefix-${T}` : never\ntype Result = DistributionProblem<'a' | 'b'>  // 'prefix-a' | 'prefix-b' (distributed)\n\n// Solution: Wrap in tuple to prevent distribution\ntype NoDistribution<T> = [T] extends [string] ? `prefix-${T}` : never\ntype Result2 = NoDistribution<'a' | 'b'>  // never (not distributed)\n\ntest_('union distribution control', () => {\n  yes_<$Equal<DistributionProblem<'a' | 'b'>, 'prefix-a' | 'prefix-b'>>()\n  yes_<$Equal<NoDistribution<'a' | 'b'>, never>>()\n})\n```\n\n---\n\n## Performance\n\n### Compilation Performance\n\nType-level operations can impact TypeScript compilation speed:\n\n#### Optimization Strategies\n\n1. **Limit Recursive Depth**\n```typescript\n// Good: Bounded recursion\ntype SafeRecursive<T, D extends number = 0> = \n  D extends 10 ? never : /* recursive logic */\n  \n// Avoid: Unbounded recursion\ntype DangerousRecursive<T> = /* infinite recursion potential */\n```\n\n2. **Use Early Returns**\n```typescript\n// Good: Early termination\ntype OptimizedCheck<T> = \n  T extends never ? $No<'never-type', []> :\n  T extends unknown ? /* continue checking */ :\n  $No<'unknown-error', []>\n  \n// Avoid: Deep nesting\ntype NestedCheck<T> = \n  T extends A ? (\n    T extends B ? (\n      T extends C ? /* very deep */ : never\n    ) : never\n  ) : never\n```\n\n3. **Cache Complex Types**\n```typescript\n// Good: Reuse computed types\ntype UserWithProfile = User & { profile: Profile }\ntype AdminWithProfile = Admin & { profile: Profile }\ntype $ValidateUserProfile = ValidateSchema<UserWithProfile, UserSchema>\n\n// Avoid: Recomputing same types\ntype $ValidateUser1 = ValidateSchema<User & { profile: Profile }, UserSchema>\ntype $ValidateUser2 = ValidateSchema<User & { profile: Profile }, UserSchema>\n```\n\n### Memory Considerations\n\n```typescript\n// Memory-efficient phantom types\nconst efficientPhantom = t_<SmallType>()    // Good\n\n// Avoid large phantom type instantiations\nconst heavyPhantom = t_<{\n  [K in string]: {\n    [J in string]: {\n      [I in string]: any  // This creates enormous types\n    }\n  }\n}>()  // Avoid\n```\n\n---\n\n## Best Practices\n\n### 1. Type Organization\n\n```typescript\n// Organize types by domain\nnamespace UserDomain {\n  export type User = { id: string; name: string }\n  export type CreateUserRequest = Omit<User, 'id'>\n  export type UpdateUserRequest = Partial<CreateUserRequest>\n  \n  export const validateUser = test_('user validation', () => {\n    const user = t_<User>()\n    is_<string>(user.id)\n    is_<string>(user.name)\n  })\n}\n\nnamespace ProductDomain {\n  export type Product = { id: string; name: string; price: number }\n  // ... product-related types\n}\n```\n\n### 2. Testing Strategy\n\n```typescript\n// Test at multiple levels\nnamespace ApiTests {\n  // Unit tests for individual types\n  export const userTypeTest = test_('user type structure', () => {\n    type User = { id: string; email: string }\n    const user = t_<User>()\n    is_<string>(user.id)\n    is_<string>(user.email)\n  })\n  \n  // Integration tests for type relationships\n  export const apiContractTest = test_('API contract compatibility', () => {\n    type ApiResponse<T> = { data: T; status: number }\n    type UserResponse = ApiResponse<User>\n    \n    const response = t_<UserResponse>()\n    is_<User>(response.data)\n    is_<number>(response.status)\n  })\n}\n```\n\n### 3. Documentation Strategy\n\n```typescript\n/**\n * Validates that a type T has all required properties of type U\n * \n * @example\n * ```typescript\n * type User = { name: string; age: number }\n * yes_<$HasRequiredProps<{ name: 'Alice', age: 30 }, User>>()  // ✓\n * no_<$HasRequiredProps<{ name: 'Alice' }, User>>()           // ❌ missing age\n * ```\n */\ntype $HasRequiredProps<T, U> = {\n  [K in keyof U]-?: K extends keyof T \n    ? T[K] extends U[K] \n      ? $Yes \n      : $No<'type-mismatch', [K, T[K], U[K]]>\n    : $No<'missing-property', [K]>\n}[keyof U]\n```\n\n### 4. T['port'] extends number\n          ? $Yes\n          : $No<'port-must-be-number', [T['port']]>\n        : $No<'missing-port-property', []>\n      : $No<'host-must-be-string', [T['host']]>\n    : $No<'missing-host-property', []>\n```\n\n---\n\n## Migration Guide\n\n### From Runtime to Type-Level Validation\n\n#### Before (Runtime)\n```typescript\nfunction validateUser(data: any): data is User {\n  return (\n    typeof data === 'object' &&\n    data !== null &&\n    typeof data.name === 'string' &&\n    typeof data.age === 'number'\n  )\n}\n```\n\n#### After (Type-Level)\n```typescript\ntest_('user validation', () => {\n  type User = { name: string; age: number }\n  const user = t_<User>()\n  \n  has_<'name', string>(user)\n  has_<'age', number>(user)\n  is_<User>(user)\n})\n```\n\n### From Manual Type Checking to Automated\n\n#### Before\n```typescript\n// Manual verification in comments\ntype ApiResponse = {\n  data: User[]    // TODO: verify this matches API\n  total: number   // TODO: check this is always present\n}\n```\n\n#### After\n```typescript\ntest_('API response contract', () => {\n  type ApiResponse = {\n    data: User[]\n    total: number\n  }\n  \n  const response = t_<ApiResponse>()\n  is_<User[]>(response.data)\n  is_<number>(response.total)\n  \n  // Verify array element type\n  const user = t_<User>()\n  extends_<User, typeof response.data[number]>()\n})\n```\n\n---\n\n## Troubleshooting\n\n### Common Issues\n\n#### Issue: \"Type instantiation is excessively deep\"\n\n**Cause**: Recursive types without proper termination\n\n**Solution**:\n```typescript\n// Add depth limiting\ntype SafeRecursive<T, Depth extends readonly any[] = []> =\n  Depth['length'] extends 10 \n    ? never  // Stop recursion\n    : /* recursive logic with Depth parameter */\n```\n\n#### Issue: \"Union type is too complex\"\n\n**Cause**: Very large union types\n\n**Solution**:\n```typescript\n// Break down large unions\ntype LargeUnion = A | B | C | D | E | F | G  // Too many members\n\n// Group related types\ntype GroupA = A | B | C\ntype GroupB = D | E | F | G\ntype ManagedUnion = GroupA | GroupB\n```\n\n#### Issue: Unexpected type distribution\n\n**Solution**:\n```typescript\n// Prevent distribution with tuple wrapping\ntype NoDistribute<T> = [T] extends [any] ? /* logic */ : never\n```\n\n### Performance Issues\n\n#### Slow compilation:\n\n1. Reduce recursive type complexity\n2. Limit phantom type size\n3. Cache computed types\n4. Use `skipLibCheck: true` in tsconfig.json for dependencies\n\n#### Memory usage:\n\n1. Avoid deeply nested phantom types\n2. Use type aliases for complex types\n3. Limit test suite size\n\n---\n\n## Conclusion\n\nType-level programming with @typefirst/typist enables powerful static analysis and verification capabilities.
