[Style Guidelines](#style-guidelines)\n\n---\n\n## Code of Conduct\n\nBy participating in this project, you agree to abide by our Code of Conduct. We are committed to providing a welcoming and inclusive environment for all contributors.\n\n### Our Standards\n\n- Be respectful and inclusive\n- Welcome newcomers and help them learn\n- Focus on constructive feedback\n- Be patient with different skill levels\n- Acknowledge different perspectives\n\n### Unacceptable Behavior\n\n- Harassment or discrimination of any kind\n- Trolling, insulting, or derogatory comments\n- Public or private harassment\n- Publishing others' private information\n- Any conduct inappropriate for a professional setting\n\n---\n\n## Getting Started\n\n### Prerequisites\n\n- Node.js 18.0.0 or later\n- npm 8.0.0 or later\n- TypeScript 4.9.0 or later\n- Git\n\n### Setting Up Your Environment\n\n1. **Fork the repository**\n   ```bash\n   # On GitHub, click \"Fork\" to create your own copy\n   ```\n\n2. **Clone your fork**\n   ```bash\n   git clone https://github.com/YOUR_USERNAME/typist.git\n   cd typist\n   ```\n\n3. **Add upstream remote**\n   ```bash\n   git remote add upstream https://github.com/type-first/typist.git\n   ```\n\n4. **Install dependencies**\n   ```bash\n   npm install\n   ```\n\n5. **Verify setup**\n   ```bash\n   npm run typecheck\n   npm run test\n   ```\n\n---\n\n## Development Setup\n\n### Available Scripts\n\n```bash\n# Type checking\nnpm run typecheck          # Check types without emitting\nnpm run build              # Build the project\n\n# Testing\nnpm run test               # Run all tests (same as typecheck)\nnpm run example            # Run example files\n\n# Development\nnpm run dev                # Start development mode (watch)\n```\n\n### Editor Setup\n\n#### VS Code (Recommended)\n\n1. Install the TypeScript extension\n2. Open the workspace file: `typist.code-workspace`\n3. Recommended settings are included in `.vscode/settings.json`\n\n#### Other Editors\n\n- Ensure TypeScript language server is enabled\n- Configure strict type checking\n- Enable editor integration for TypeScript errors\n\n---\n\n## Project Structure\n\n```\ntypist/\n├── src/                    # Source code\n│   ├── index.ts           # Main entry point\n│   ├── assertions.ts      # Type assertion utilities\n│   ├── comparators.ts     # Type comparison operations\n│   ├── verdicts.ts        # Verdict type definitions\n│   ├── operators.ts       # Phantom type operators\n│   └── blocks.ts          # Test organization utilities\n├── examples/              # Usage examples\n│   └── get-path.ts       # Path-based access example\n├── docs/                  # Documentation\n│   ├── api.md            # API reference\n│   ├── guide.md          # Usage guide\n│   ├── examples.md       # Example documentation\n│   └── contributing.md   # This file\n├── tests/                 # Test files (type-level tests)\n├── package.json          # Package configuration\n├── tsconfig.json         # TypeScript configuration\n├── CHANGELOG.md          # Version history\n└── README.md             # Project overview\n```\n\n### Module Organization\n\n- **`assertions.ts`**: Functions that test type relationships\n- **`comparators.ts`**: Types that return verdicts for comparisons\n- **`verdicts.ts`**: Verdict types (`$Yes`, `$No`, etc.)\n- **`operators.ts`**: Phantom type creation and manipulation\n- **`blocks.ts`**: Test organization utilities (`test_`, `example_`, etc.)\n\n---\n\n## Development Workflow\n\n### 1. Choose an Issue\n\n- Check [existing issues](https://github.com/type-first/typist/issues)\n- Look for issues labeled `good first issue` for beginners\n- Comment on the issue to indicate you're working on it\n\n### 2. Create a Feature Branch\n\n```bash\n# Update your main branch\ngit checkout main\ngit pull upstream main\n\n# Create a new branch\ngit checkout -b feature/your-feature-name\n# or\ngit checkout -b fix/issue-description\n```\n\n### 3. Make Your Changes\n\n- Follow the [Style Guidelines](#style-guidelines)\n- Add tests for new functionality\n- Update documentation as needed\n- Keep commits focused and atomic\n\n### 4. Test Your Changes\n\n```bash\n# Run type checking\nnpm run typecheck\n\n# Test examples\nnpm run example\n\n# Run any specific tests\n```\n\n### 5. Commit Your Changes\n\n```bash\n# Add files\ngit add .\n\n# Commit with descriptive message\ngit commit -m \"feat: add new phantom type utility\"\n# or\ngit commit -m \"fix: resolve issue with type inference\"\n# or\ngit commit -m \"docs: update API documentation\"\n```\n\n### Commit Message Format\n\nWe follow the [Conventional Commits](https://conventionalcommits.org/) specification:\n\n```\n<type>(<scope>): <description>\n\n[optional body]\n\n[optional footer]\n```\n\n**Types:**\n- `feat`: New feature\n- `fix`: Bug fix\n- `docs`: Documentation changes\n- `test`: Adding or updating tests\n- `refactor`: Code refactoring\n- `perf`: Performance improvements\n- `chore`: Maintenance tasks\n\n**Examples:**\n```\nfeat(operators): add new intersect_ utility\nfix(assertions): resolve never_ type inference issue\ndocs(api): update phantom type documentation\ntest: add comprehensive form validation examples\n```\n\n---\n\n## Testing Guidelines\n\n### Type-Level Testing\n\nSince typist is a type-level library, testing primarily involves type checking:\n\n```typescript\nimport { test_, is_, yes_, never_, $Equal } from '@typefirst/typist'\n\n// Test your new utility\ntest_('new utility validation', () => {\n  // Test basic functionality\n  const result = yourNewUtility<string>()\n  is_<string>(result)\n  \n  // Test edge cases\n  never_<yourNewUtility<never>()>\n  \n  // Test with complex types\n  type ComplexType = { nested: { value: number } }\n  const complex = yourNewUtility<ComplexType>()\n  is_<number>(complex.nested.value)\n  \n  // Test type relationships\n  yes_<$Equal<ExpectedType, typeof result>>()\n})\n```\n\n### Test Categories\n\n1. **Unit Tests**: Test individual utilities in isolation\n2. **Integration Tests**: Test utilities working together\n3. **Edge Case Tests**: Test boundary conditions and error cases\n4. **Example Tests**: Test real-world usage patterns\n\n### Test File Organization\n\n```typescript\n// tests/operators.test.ts\nimport { test_, phantom_, is_, extends_ } from '../src'\n\ntest_('phantom_ utility', () => {\n  // Basic usage\n  const str = phantom_<string>()\n  is_<string>(str)\n  \n  // With complex types\n  type User = { name: string; age: number }\n  const user = phantom_<User>()\n  is_<string>(user.name)\n  is_<number>(user.age)\n})\n\ntest_('intersect_ utility', () => {\n  // Test intersection behavior\n  const combined = intersect_<{ a: string }, { b: number }>()\n  is_<string>(combined.a)\n  is_<number>(combined.b)\n  \n  // Test with primitives\n  const primitive = intersect_<string, number>()  \n  never_<typeof primitive>()  // string & number is never\n})\n```\n\n---\n\n## Documentation Guidelines\n\n### Code Documentation\n\n```typescript\n/**\n * Creates a phantom value of type T with optional runtime value.\n * \n * Phantom types allow you to represent type information without\n * corresponding runtime values, enabling type-level programming.\n * \n * @template T - The type to create a phantom value for\n * @param x - Optional runtime value (ignored at runtime)\n * @returns Phantom value of type T\n * \n * @example\n * ```typescript\n * const user = phantom_<{ name: string; age: number }>()\n * is_<string>(user.name)  // ✓ Type assertion passes\n * is_<number>(user.age)   // ✓ Type assertion passes\n * ```\n * \n * @example\n * ```typescript\n * // With optional runtime value for debugging\n * const debugUser = phantom_<User>({ debug: 'user-phantom' })\n * ```\n */\nexport const phantom_ = <T>(x: unknown = null): T => x as T\n```\n\n### API Documentation\n\n- Use JSDoc comments for all public APIs\n- Include type parameters and their constraints\n- Provide usage examples\n- Document edge cases and limitations\n- Link to related utilities\n\n### README and Guides\n\n- Use clear, concise language\n- Provide working code examples\n- Include both simple and complex use cases\n- Explain the \"why\" not just the \"how\"\n- Keep examples up-to-date with the API\n\n---\n\n## Pull Request Process\n\n### Before Submitting\n\n1. **Ensure all tests pass**\n   ```bash\n   npm run typecheck\n   npm run test\n   ```\n\n2. **Update documentation**\n   - Add or update API documentation\n   - Update examples if needed\n   - Add entry to CHANGELOG.md\n\n3. **Sync with upstream**\n   ```bash\n   git fetch upstream\n   git rebase upstream/main\n   ```\n\n### Submitting Your PR\n\n1. **Push to your fork**\n   ```bash\n   git push origin feature/your-feature-name\n   ```\n\n2. **Create Pull Request**\n   - Go to GitHub and create a new pull request\n   - Use the PR template\n   - Link related issues\n   - Provide clear description of changes\n\n### PR Template\n\n```markdown\n## Description\nBrief description of the changes made.\n\n## Type of Change\n- [ ] Bug fix (non-breaking change that fixes an issue)\n- [ ] New feature (non-breaking change that adds functionality)\n- [ ] Breaking change (fix or feature that would cause existing functionality to not work as expected)\n- [ ] Documentation update\n\n## Testing\n- [ ] Type checking passes\n- [ ] Added tests for new functionality\n- [ ] All existing tests pass\n- [ ] Examples work correctly\n\n## Documentation\n- [ ] Updated API documentation\n- [ ] Updated README if needed\n- [ ] Added/updated examples\n- [ ] Updated CHANGELOG.md\n\n## Related Issues\nFixes #(issue number)\n\n## Additional Notes\nAny additional information about the changes.\n```\n\n### Review Process\n\n1. **Automated Checks**: CI runs type checking and tests\n2. **Code Review**: Maintainers review code quality and design\n3. **Documentation Review**: Ensure documentation is complete and accurate\n4. **Final Approval**: At least one maintainer approval required\n\n---\n\n## Release Process\n\n### Version Numbering\n\nWe follow [Semantic Versioning](https://semver.org/):\n\n- **MAJOR**: Breaking changes\n- **MINOR**: New features (backward compatible)\n- **PATCH**: Bug fixes (backward compatible)\n\n### Release Steps\n\n1. **Update Version**\n   ```bash\n   npm version patch|minor|major\n   ```\n\n2. **Update CHANGELOG.md**\n   - Add new version section\n   - List all changes since last release\n   - Categorize changes (Added, Changed, Fixed, Removed)\n\n3. **Create Release**\n   ```bash\n   git push origin main --tags\n   ```\n\n4. **Publish to npm**\n   ```bash\n   npm publish\n   ```\n\n5. **Create GitHub Release**\n   - Create release from tag\n   - Include changelog information\n   - Highlight major changes\n\n---\n\n## Style Guidelines\n\n### TypeScript Code Style\n\n```typescript\n// Use descriptive names with underscore suffix for utilities\nexport const phantom_ = <T>(x?: unknown): T => x as T\nexport const is_ = <T>(x: T) => {}\n\n// Use clear type parameter names\ntype GetAtPath<Obj, Path extends readonly PropertyKey[]> = /* ... */\n\n// Use consistent formatting\ntype ComplexType<T> = T extends SomeCondition\n  ? ResultIfTrue\n  : T extends AnotherCondition\n    ? ResultIfSecondTrue\n    : DefaultResult\n\n// Group related exports\nexport const {\n  phantom_,\n  type_,\n  t_,\n  assign_,\n  a_\n} = /* ... */\n```\n\n### Documentation Style\n\n```typescript\n// Use clear, concise comments\n/**\n * Tests whether a value is assignable to type T.\n * \n * This utility performs a compile-time assignability check,\n * ensuring the provided value matches the expected type.\n */\n\n// Prefer examples over lengthy explanations\n/**\n * @example\n * ```typescript\n * is_<string>('hello')     // ✓ Passes\n * is_<number>(42)          // ✓ Passes\n * // is_<string>(123)      // ❌ Type error\n * ```\n */\n```\n\n### Naming Conventions\n\n- **Functions**: `camelCase` with underscore suffix (`phantom_`, `is_`)\n- **Types**: `PascalCase` (`GetAtPath`, `ValidationSchema`)\n- **Verdict Types**: `$PascalCase` with dollar prefix (`$Yes`, `$No`, `$Equal`)\n- **Type Parameters**: Single uppercase letters or descriptive names (`T`, `K`, `Obj`, `Path`)\n- **Private/Internal**: Underscore prefix (`_internal`, `_helper`)\n\n### File Organization\n\n```typescript\n// 1. Imports\nimport { $Yes, $No } from './verdicts'\n\n// 2. Type definitions\nexport type SomeType<T> = /* ... */\n\n// 3. Utility functions\nexport const utility_ = <T>(x: T) => /* ... */\n\n// 4. Aliases and shortcuts\nexport const u_ = utility_\nexport const short_ = utility_\n```\n\n---\n\n## Getting Help\n\n### Resources\n\n- **Documentation**: [API Reference](api.md), [Usage Guide](guide.md)\n- **Examples**: [Examples Documentation](examples.md)\n- **Issues**: [GitHub Issues](https://github.com/type-first/typist/issues)\n- **Discussions**: [GitHub Discussions](https://github.com/type-first/typist/discussions)\n\n### Asking Questions\n\nWhen asking for help:\n\n1. **Search existing issues and discussions first**\n2. **Provide minimal reproducible example**\n3. **Include TypeScript version and configuration**\n4. **Describe expected vs. actual behavior**\n5. **Include relevant error messages**\n\n### Example Issue Template\n\n```markdown\n## Problem Description\nClear description of the issue or question.\n\n## Code Example\n```typescript\n// Minimal example that reproduces the issue\nimport { is_, t_ } from '@typefirst/typist'\n\nconst example = t_<{ name: string }>()\nis_<string>(example.name)  // Expected to pass but fails\n```\n\n## Environment\n- TypeScript version: 5.0.0\n- Node.js version: 18.0.0\n- @typefirst/typist version: 1.0.0\n\n## Expected Behavior\nWhat you expected to happen.\n\n## Actual Behavior\nWhat actually happened, including error messages.\n```\n\n---\n\n## Recognition\n\nWe appreciate all contributions!
