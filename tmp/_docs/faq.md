They complement each other perfectly:\n\n```typescript\nimport { z } from 'zod'\nimport { test_, is_, has_, t_ } from '@typefirst/typist'\n\n// Runtime validation for external data\nconst UserSchema = z.object({\n  id: z.string(),\n  email: z.string().email(),\n  age: z.number().min(0)\n})\n\ntype User = z.infer<typeof UserSchema>\n\n// Compile-time validation for type safety\ntest_('user type validation', () => {\n  const user = t_<User>()\n  is_<string>(user.id)\n  is_<string>(user.email)\n  is_<number>(user.age)\n})\n\n// Use both for maximum safety\nfunction processApiData(rawData: unknown) {\n  const user = UserSchema.parse(rawData) // Runtime validation\n  // user now has User type with both runtime and compile-time safety\n  return user\n}\n```\n\n---\n\n## Getting Started\n\n### Q: What are the minimum requirements to use typist?\n\n**A:** \n- **TypeScript:** 4.9.0 or later\n- **Node.js:** 18.0.0 or later\n- **Build setup:** Any TypeScript build system (tsc, webpack, vite, etc.)\n\n### Q: How do I install and start using typist?\n\n**A:**\n\n```bash\nnpm install @typefirst/typist\n```\n\n```typescript\nimport { t_, is_, test_, $Equal, yes_ } from '@typefirst/typist'\n\n// Create phantom types\nconst user = t_<{ name: string; age: number }>()\n\n// Test type relationships\ntest_('basic validation', () => {\n  is_<string>(user.name)\n  is_<number>(user.age)\n  yes_<$Equal<typeof user.age, number>>()\n})\n```\n\n### Q: Do I need to change my build configuration?\n\n**A:** No special configuration needed! typist works with any TypeScript setup. All utilities are compile-time only and get eliminated during compilation.\n\n### Q: Can I use typist in JavaScript projects?\n\n**A:** typist is specifically designed for TypeScript's type system. For JavaScript projects, consider:\n- Migrating to TypeScript to use typist\n- Using runtime validation libraries instead\n- Using TypeScript for type checking with `checkJs: true`\n\n---\n\n## Type System Concepts\n\n### Q: What are phantom types and how do they work?\n\n**A:** Phantom types represent type information without runtime values:\n\n```typescript\nimport { t_, phantom_ } from '@typefirst/typist'\n\n// Creates a value that has User type but no runtime representation\nconst user = t_<{ name: string; age: number }>()\n\n// This compiles to nothing in JavaScript\nconsole.log(user) // undefined at runtime\n\n// But provides full type information for validation\nis_<string>(user.name)  // ✓ Type checking works\nis_<number>(user.age)   // ✓ TypeScript knows the structure\n```\n\n**Why useful:**\n- Test type relationships without creating actual objects\n- Manipulate types as first-class values\n- Zero runtime overhead\n- Enable type-level programming\n\n### Q: What are verdicts and how do they work?\n\n**A:** Verdicts encode the results of type-level computations:\n\n```typescript\nimport { $Equal, $Extends, yes_, no_ } from '@typefirst/typist'\n\n// Successful comparisons return $Yes\ntype IsEqual = $Equal<string, string>        // → $Yes\ntype DoesExtend = $Extends<'hello', string>  // → $Yes\n\n// Failed comparisons return $No with error details\ntype NotEqual = $Equal<string, number>       // → $No<'not-equal', [string, number]>\ntype NoExtend = $Extends<string, number>     // → $No<'right-does-not-extend-left', [string, number]>\n\n// Use in assertions\nyes_<IsEqual>()    // ✓ Assertion passes\nno_<NotEqual>()    // ✓ Assertion passes for negative verdict\n```\n\n### Q: How do I understand complex type error messages?\n\n**A:** Break down complex assertions into smaller steps:\n\n```typescript\n// Instead of one complex assertion\n// is_<ComplexExpectedType>(veryComplexExpression)\n\n// Break into steps for better error messages\ntype Step1 = SomeTransformation<InputType>\ntype Step2 = AnotherTransformation<Step1>\n\ntest_('step by step validation', () => {\n  const step1 = t_<Step1>()\n  const step2 = t_<Step2>()\n  \n  is_<ExpectedStep1>(step1)  // Clear error if Step1 is wrong\n  is_<ExpectedStep2>(step2)  // Clear error if Step2 is wrong\n})\n```\n\n---\n\n## Performance and Optimization\n\n### Q: Does typist affect my application's runtime performance?\n\n**A:** No! typist has **zero runtime impact**:\n\n```typescript\n// This code:\nconst user = t_<{ name: string }>()\nis_<string>(user.name)\ntest_('validation', () => {\n  yes_<$Equal<string, string>>()\n})\n\n// Compiles to:\n// (completely empty - all code is eliminated)\n```\n\n**Verification:**\n```bash\n# Check your bundle size before and after adding typist\nnpm run build\n# Bundle size should be identical\n```\n\n### Q: Can typist slow down TypeScript compilation?\n\n**A:** Complex type operations can impact compilation, but typical usage has minimal effect:\n\n**Good practices:**\n- Use simple assertions for most validation\n- Limit recursive type depth\n- Cache complex computed types\n- Avoid very large union types\n\n**Monitor compilation performance:**\n```bash\ntsc --extendedDiagnostics\n# Watch \"Check time\" metric\n```\n\n### Q: How can I optimize compilation performance?\n\n**A:**\n\n1. **Limit recursion depth:**\n```typescript\n// Add termination conditions\ntype SafeRecursive<T, D extends readonly any[] = []> = \n  D['length'] extends 10 ? never : /* recursive logic */\n```\n\n2. **Use helper types:**\n```typescript\n// Cache common patterns\ntype ApiResponse<T> = { data: T; status: number }\ntype UserResponse = ApiResponse<User>  // Reuse pattern\n```\n\n3. **Break down complex types:**\n```typescript\n// Instead of one complex type\ntype Complex<T> = /* very complex conditional type */\n\n// Use multiple simpler types\ntype CheckA<T> = /* simpler check */\ntype CheckB<T> = /* another check */\ntype Complex<T> = CheckA<T> extends true ? CheckB<T> : never\n```\n\n---\n\n## Debugging and Troubleshooting\n\n### Q: Why am I getting \"Type instantiation is excessively deep\" errors?\n\n**A:** This usually indicates unbounded recursive types:\n\n**Problem:**\n```typescript\ntype BadRecursive<T> = {\n  value: T\n  nested: BadRecursive<T>  // No termination!\n}\n```\n\n**Solution:**\n```typescript\n// Add depth limits\ntype GoodRecursive<T, Depth extends readonly any[] = []> = \n  Depth['length'] extends 5  // Limit recursion\n    ? never\n    : {\n        value: T\n        nested?: GoodRecursive<T, [0, ...Depth]>\n      }\n```\n\n### Q: My type assertions are failing but they look correct. What's wrong?\n\n**A:** Common issues:\n\n1. **Exact matching problems:**\n```typescript\n// Problem: Structural vs exact matching\ntype User = { name: string }\ntype UserWithExtra = { name: string; extra: number }\n\n// This fails - UserWithExtra is not exactly User\n// is_<User>(someUserWithExtra)\n\n// Solution: Use extends for structural compatibility\nextends_<UserWithExtra, User>()  // ✓ Works\n```\n\n2. **Readonly/mutable differences:**\n```typescript\n// Problem: readonly vs mutable arrays\nconst readonlyArray = ['a', 'b'] as const\n// is_<string[]>(readonlyArray)  // ❌ Fails\n\n// Solution: Use correct type or extends\nis_<readonly string[]>(readonlyArray)  // ✓ Works\nextends_<typeof readonlyArray, readonly string[]>()  // ✓ Works\n```\n\n3. **Union distribution:**\n```typescript\n// Problem: Unexpected union distribution\ntype Test<T> = T extends string ? `prefix-${T}` : never\ntype Result = Test<'a' | 'b'>  // 'prefix-a' | 'prefix-b' (distributed)\n\n// Solution: Prevent distribution with tuple\ntype Test<T> = [T] extends [string] ? `prefix-${T}` : never\ntype Result = Test<'a' | 'b'>  // never (not distributed)\n```\n\n### Q: How do I debug complex type-level operations?\n\n**A:**\n\n1. **Use type annotations to inspect intermediate results:**\n```typescript\ntest_('debugging complex types', () => {\n  type Input = { a: string; b: number }\n  \n  // Debug step by step\n  type Keys = keyof Input        // 'a' | 'b'\n  type Values = Input[Keys]      // string | number\n  type Mapped = { [K in Keys]: Values }  // Final result\n  \n  // Verify each step\n  yes_<$Equal<Keys, 'a' | 'b'>>()\n  yes_<$Equal<Values, string | number>>()\n})\n```\n\n2. **Use conditional type debugging:**\n```typescript\n// Add debug branches to understand flow\ntype Debug<T> = \n  T extends string ? { debug: 'is-string'; type: T } :\n  T extends number ? { debug: 'is-number'; type: T } :\n  { debug: 'unknown'; type: T }\n\ntype DebugResult = Debug<'hello'>  // { debug: 'is-string'; type: 'hello' }\n```\n\n---\n\n## Best Practices\n\n### Q: When should I use typist vs regular TypeScript types?\n\n**A:**\n\n**Use typist for:**\n- Testing type relationships and constraints\n- Validating API contracts and interfaces\n- Building type-safe libraries with complex generics\n- Creating examples and documentation\n- Proving type-level invariants\n\n**Use regular TypeScript for:**\n- Basic type annotations\n- Simple interface definitions\n- Function parameter and return types\n- Standard generic constraints\n\n### Q: How should I organize my type-level tests?\n\n**A:**\n\n```typescript\n// Group by domain/module\nnamespace UserDomain {\n  export const typeValidation = test_('user types', () => {\n    const user = t_<User>()\n    is_<string>(user.id)\n    is_<string>(user.email)\n  })\n  \n  export const apiValidation = test_('user API contracts', () => {\n    const response = t_<GetUserResponse>()\n    has_<'user', User>(response)\n  })\n}\n\nnamespace ProductDomain {\n  // Product-related validations\n}\n```\n\n### Q: Should I write type tests for every type in my codebase?\n\n**A:** Focus on testing:\n\n**High priority:**\n- Public API interfaces\n- Complex generic types\n- Type utilities and transformations\n- Critical business logic types\n\n**Lower priority:**\n- Simple interfaces with primitive types\n- Types that are tested implicitly through usage\n- Internal implementation details\n\n**Example strategy:**\n```typescript\n// Test complex/critical types\ntest_('API contract validation', () => {\n  type ComplexApiResponse = /* complex type */\n  // Comprehensive testing here\n})\n\n// Simple types often don't need explicit tests\ntype UserId = string  // No test needed\ntype UserEmail = string  // No test needed\n```\n\n### Q: How do I handle breaking type changes?\n\n**A:**\n\n1. **Version your type interfaces:**\n```typescript\nnamespace ApiV1 {\n  export type User = { id: string; name: string }\n}\n\nnamespace ApiV2 {\n  export type User = { id: string; firstName: string; lastName: string }\n}\n\n// Test backward compatibility\ntest_('API version compatibility', () => {\n  // Ensure V2 can handle V1 data structure transformations\n  type V1ToV2 = {\n    id: ApiV1.User['id']\n    firstName: string\n    lastName: string\n  }\n  \n  extends_<V1ToV2, ApiV2.User>()\n})\n```\n\n2. **Use deprecation patterns:**\n```typescript\n// Mark deprecated types\n/** @deprecated Use NewUserType instead */\ntype OldUserType = { /* old structure */ }\n\ntype NewUserType = { /* new structure */ }\n\n// Test migration path\ntest_('migration validation', () => {\n  // Ensure new type can represent old data\n  const oldData = t_<OldUserType>()\n  const newData = transformOldToNew(oldData)\n  is_<NewUserType>(newData)\n})\n```\n\n---\n\n## Advanced Usage\n\n### Q: How do I create custom type comparators?\n\n**A:**\n\n```typescript\nimport { $Yes, $No } from '@typefirst/typist'\n\n// Custom comparator for array length\ntype $ArrayLengthEqual<T1 extends readonly any[], T2 extends readonly any[]> =\n  T1['length'] extends T2['length']\n    ? T2['length'] extends T1['length']\n      ? $Yes\n      : $No<'length-mismatch', [T1['length'], T2['length']]>\n    : $No<'length-mismatch', [T1['length'], T2['length']]>\n\n// Usage\ntest_('custom array length comparison', () => {\n  type Same = $ArrayLengthEqual<[1, 2, 3], ['a', 'b', 'c']>     // $Yes\n  type Different = $ArrayLengthEqual<[1, 2], [1, 2, 3]>        // $No<...>\n  \n  yes_<Same>()\n  no_<Different>()\n})\n```\n\n### Q: How do I validate complex recursive data structures?\n\n**A:**\n\n```typescript\n// Define recursive structure\ntype TreeNode<T> = {\n  value: T\n  children: TreeNode<T>[]\n}\n\n// Validate with depth limits\ntype ValidateTree<T, D extends readonly any[] = []> = \n  D['length'] extends 5 ? $Yes :  // Assume valid at max depth\n  T extends { value: infer V; children: infer C }\n    ? C extends TreeNode<V>[]\n      ? $Yes\n      : $No<'invalid-children', [C]>\n    : $No<'invalid-structure', [T]>\n\ntest_('recursive tree validation', () => {\n  type StringTree = TreeNode<string>\n  const tree = t_<StringTree>()\n  \n  is_<string>(tree.value)\n  is_<StringTree[]>(tree.children)\n  yes_<ValidateTree<StringTree>>()\n})\n```\n\n### Q: How do I build type-safe state machines?\n\n**A:**\n\n```typescript\n// Define states and transitions\ntype OrderState = 'draft' | 'submitted' | 'processing' | 'shipped' | 'delivered'\n\ntype OrderTransitions = {\n  draft: 'submitted'\n  submitted: 'processing' | 'cancelled'\n  processing: 'shipped' | 'cancelled'\n  shipped: 'delivered'\n  delivered: never\n}\n\n// Validate transitions\ntype $ValidTransition<From extends OrderState, To extends OrderState> =\n  To extends OrderTransitions[From] \n    ? $Yes \n    : $No<'invalid-transition', [From, To]>\n\ntest_('state machine validation', () => {\n  yes_<$ValidTransition<'draft', 'submitted'>>()\n  yes_<$ValidTransition<'submitted', 'processing'>>()\n  no_<$ValidTransition<'delivered', 'processing'>>()\n  no_<$ValidTransition<'shipped', 'draft'>>()\n})\n```\n\n---\n\n## Migration and Integration\n\n### Q: How do I gradually migrate from runtime validation to type-level validation?\n\n**A:** Use a phased approach:\n\n**Phase 1: Add type-level validation alongside existing runtime validation**\n```typescript\n// Keep existing runtime validation\nfunction validateUser(data: unknown): data is User {\n  // existing validation logic\n}\n\n// Add type-level validation\ntest_('user type validation', () => {\n  const user = t_<User>()\n  is_<string>(user.id)\n  is_<string>(user.email)\n})\n```\n\n**Phase 2: Use both for comprehensive coverage**\n```typescript\nfunction processUserData(rawData: unknown) {\n  if (!validateUser(rawData)) {\n    throw new Error('Invalid user data')\n  }\n  // rawData is now typed as User with both runtime and compile-time safety\n  return transformUser(rawData)\n}\n```\n\n**Phase 3: Replace internal validation with type-level only**\n```typescript\n// For internal functions, rely on TypeScript types\nfunction transformUser(user: User): TransformedUser {\n  // No runtime validation needed - TypeScript ensures type safety\n  return {\n    id: user.id,\n    displayName: `${user.firstName} ${user.lastName}`\n  }\n}\n```\n\n### Q: Can I use typist with existing testing frameworks?\n\n**A:** Yes! typist complements traditional testing:\n\n```typescript\n// Traditional
